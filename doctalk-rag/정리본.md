> 그리고 Karpathy LLM Wiki 패턴을 어떻게 적용했는지를 비개발자도 이해할 수 있도록 정리한 문서.

## Part 1. 기초 개념 — AI가 "아는 척"이 아니라 "진짜 아는" 답변을 하려면

---

### 1.1 LLM이란 무엇인가?

**LLM (Large Language Model, 대규모 언어 모델)** 은 방대한 양의 텍스트를 학습한 AI 모델이다.
ChatGPT, Gemini, Claude 같은 서비스가 모두 LLM을 기반으로 동작한다.

**비유**: LLM은 수천만 권의 책을 읽은 박학다식한 사람과 비슷하다.

- 일반적인 질문에는 꽤 정확한 답을 한다
- 대화를 자연스럽게 이어가고, 요약하고, 번역할 수 있다
- 새로운 글을 생성하거나, 기존 글을 분석할 수 있다

**LLM의 한계**:

| 한계 | 설명 | 예시 |
|------|------|------|
| 학습 마감일 | 학습 이후의 정보를 모른다 | "어제 나온 신약에 대해 알려줘" → 모름 |
| 환각 (Hallucination) | 모르는 것도 그럴듯하게 지어낸다 | 존재하지 않는 논문을 인용 |
| 내 데이터를 모름 | 우리 병원 정보, 환자 기록을 모른다 | "김OO 환자의 최근 검사 결과는?" → 모름 |
| 토큰 제한 | 한 번에 읽을 수 있는 텍스트 양에 한계가 있다 | 환자 183회 방문 기록을 한꺼번에 못 읽음 |

**핵심 포인트**: LLM은 "세상의 일반 지식"은 잘 알지만, "우리 병원만의 지식"은 전혀 모른다. 이 문제를 해결하는 것이 RAG이다.

---

### 1.2 RAG란 무엇인가?

**RAG (Retrieval-Augmented Generation, 검색 증강 생성)** 은 AI가 답변하기 전에 관련 자료를 먼저 찾아보게 하는 기술이다.

**비유**: 오픈북 시험과 같다.

| 방식 | 비유 | 장단점 |
|------|------|--------|
| LLM만 사용 | 머릿속 기억만으로 시험 보기 | 빠르지만, 기억이 틀릴 수 있음 |
| RAG 적용 | 교과서를 펼쳐놓고 시험 보기 | 좀 더 느리지만, 정확한 근거가 있음 |

**RAG의 작동 과정 (3단계)**:

```
[1단계] 사전 준비 — 교과서 만들기
우리 병원의 자료(EMR, 파일, 정책 등)를 AI가 검색할 수 있는 형태로 가공해서 저장해둔다.

[2단계] 질문이 들어오면 — 교과서에서 찾기
환자가 "저 다음 검진 언제예요?"라고 물으면, 그 환자의 방문 기록과 병원 정책에서 관련 내용을 찾는다.

[3단계] 답변 생성 — 찾은 내용을 참고해서 대답하기
LLM이 찾아온 자료를 읽고, 그 내용을 바탕으로 자연스러운 답변을 생성한다.
```

**한 줄 정리**: RAG = "AI에게 우리 자료를 먼저 읽게 한 뒤 답변하게 하는 기술"

---

### 1.3 RAG와 LLM의 관계

RAG와 LLM은 경쟁 관계가 아니라 **협력 관계**이다.

```
LLM 단독       →  "똑똑하지만 우리 병원을 모르는 의사"
RAG + LLM      →  "똑똑하고, 환자 차트를 미리 읽고 온 의사"
```

| 역할 | 담당 | 비유 |
|------|------|------|
| RAG | 관련 자료를 찾아서 전달 | 간호사가 차트를 미리 준비 |
| LLM | 전달받은 자료를 읽고 답변 생성 | 의사가 차트를 보고 상담 |

**왜 둘 다 필요한가?**
- LLM 없이 RAG만 있으면: 자료는 찾았는데 자연스러운 답변을 못 만든다
- RAG 없이 LLM만 있으면: 답변은 유창하지만 우리 병원 정보를 모른다 (혹은 지어낸다)

---

### 1.4 핵심 용어 사전 (비개발자용)

| 용어 | 쉬운 설명 |
|------|----------|
| **임베딩 (Embedding)** | 텍스트를 숫자 배열로 변환하는 것. "고혈압"과 "혈압이 높다"가 비슷한 의미라는 것을 컴퓨터가 이해하게 해준다 |
| **벡터 (Vector)** | 임베딩의 결과물. 텍스트의 "의미"를 담은 숫자 리스트. 의미가 비슷한 문장은 벡터도 비슷하다 |
| **벡터DB** | 벡터를 저장하고, "비슷한 의미"를 빠르게 검색할 수 있는 데이터베이스 |
| **청킹 (Chunking)** | 긴 문서를 적절한 크기로 잘라내는 것. 500페이지 책을 챕터별로 나누는 것과 비슷하다 |
| **토큰 (Token)** | AI가 텍스트를 읽는 단위. 대략 한글 1~2글자 = 1토큰. AI에게 전달할 수 있는 토큰 수에는 한계가 있다 |
| **프롬프트 (Prompt)** | AI에게 주는 지시문. "당신은 OO병원 의사입니다" 같은 역할 설정도 프롬프트의 일부이다 |
| **컨텍스트 (Context)** | AI에게 전달하는 배경 정보. 환자 기록, 병원 정보 등이 여기에 들어간다 |
| **환각 (Hallucination)** | AI가 없는 사실을 그럴듯하게 지어내는 현상 |
| **PHI / PII** | 개인건강정보(PHI) / 개인식별정보(PII). 주민번호, 이름, 전화번호 등 보호해야 할 민감 정보 |
| **스트리밍 (Streaming)** | AI 답변을 한 글자씩 실시간으로 보여주는 것. 카카오톡에서 상대방이 타이핑하는 것처럼 보인다 |
| **리랭킹 (Reranking)** | 검색 결과의 순서를 다시 매기는 것. 가장 관련 있는 자료가 맨 위로 오도록 재정렬 |

## Part 2. 닥톡 AI Agent는 어떻게 작동하는가

---

### 2.1 전체 흐름 — 환자 질문부터 AI 답변까지

환자가 닥톡AI에게 "저 혈압약 언제 먹어요?"라고 물었을 때 벌어지는 일:

```
[환자 질문] "저 혈압약 언제 먹어요?"
     │
     ▼
[1. 안전 검사] 응급 상황인가? (흉통, 자살 등) → 응급이면 즉시 119 안내
     │ (응급 아님 → 계속 진행)
     ▼
[2. 환자 요약지 확인] 이 환자의 "요약지(Wiki)"가 있는가?
     │ ✅ 있으면 → 요약지 사용 (빠름)
     │ ❌ 없으면 → 원본 데이터에서 검색
     ▼
[3. 지식 검색 (RAG)] 의사 지식 + 병원 정책 + 환자 기록에서 관련 내용 찾기
     │ → 50개 후보를 찾고 → 12개로 줄이고 → 6~10개 최종 선택
     ▼
[4. 컨텍스트 구성] 찾은 자료를 AI가 읽을 수 있는 분량으로 정리
     │ → 환자 정보 1500토큰 + RAG 자료 3000토큰 = 총 4500토큰
     ▼
[5. AI 답변 생성] Gemini Flash가 자료를 읽고 자연스러운 답변 작성
     │ → 실시간 스트리밍으로 환자에게 전달
     ▼
[6. 답변 안전 검사] 확정 진단 표현은 없는가? 개인정보가 노출되지 않는가?
     │ → 문제 있으면 자동 수정
     ▼
[7. 학습] AI의 답변을 환자 기록에 저장 → 다음번에 더 좋은 답변 가능
     │
     ▼
[상담 종료 시] 전체 대화를 자동 요약 → 의사에게 제공
```

---

### 2.2 사전 준비 — 지식을 AI가 검색할 수 있게 만들기

AI가 우리 병원 자료를 검색하려면, 먼저 자료를 가공해서 저장해야 한다.

**어떤 자료를 넣을 수 있나? (17종)**

| 분류 | 자료 종류 | 중요도 |
|------|----------|--------|
| 필수 | 전자의무기록(EMR), 진단 코드 | 최고 |
| 핵심 | 의사 진료 스타일, 환자 데이터 | 매우 높음 |
| 권장 | 건강검진, 병원 정책, 엑셀, FAQ | 높음 |
| 선택 | 예방접종, 유튜브, 구글드라이브, 파일 | 보통 |

**가공 과정 (파이프라인)**:

```
원본 자료 (PDF, 텍스트, EMR 등)
     │
     ▼
[1. 파싱] 자료에서 텍스트를 추출한다
     │
     ▼
[2. 청킹] 긴 문서를 적절한 크기(약 2000자)로 자른다
     │       → 의료 문서는 섹션별로 자동 분리 (혈액검사, 종합판정 등)
     │       → 잘린 부분 사이에 20% 겹침을 두어 맥락이 끊기지 않게 한다
     ▼
[3. 임베딩] 각 조각의 "의미"를 숫자 배열(벡터)로 변환한다
     │       → "고혈압 치료"와 "혈압 관리"가 비슷한 벡터를 갖게 된다
     ▼
[4. 저장] 벡터DB에 저장한다
            → 나중에 "이 질문과 비슷한 의미의 자료"를 빠르게 찾을 수 있다
```

**중복 방지**: 같은 내용이 두 번 저장되지 않도록 내용의 "지문(해시)"을 비교한다.

**ALS (Agent Learning Score)**: 의사가 얼마나 많은 종류의 자료를 학습시켰는지 점수화. EMR과 진단 코드가 가장 높은 점수, 유튜브나 미디어가 가장 낮은 점수.

---

### 2.3 임베딩 — "의미"를 숫자로 바꾸는 기술

**왜 필요한가?**

컴퓨터는 "고혈압"과 "혈압이 높다"가 같은 의미라는 것을 글자만 보고는 모른다. 임베딩은 텍스트의 의미를 숫자로 바꿔서 컴퓨터가 "의미의 유사도"를 계산할 수 있게 해준다.

**비유**: 지도에 핀을 꽂는 것과 비슷하다.
- "고혈압"과 "혈압이 높다"는 지도에서 가까운 곳에 핀이 꽂힌다
- "고혈압"과 "맛있는 피자"는 지도에서 먼 곳에 핀이 꽂힌다
- 질문이 들어오면, 질문의 핀 위치에서 가장 가까운 자료의 핀을 찾는다

**닥톡의 임베딩 최적화 (TurboQuant)**:

일반적으로 임베딩은 1536개의 숫자로 구성되는데, 닥톡은 이를 3단계로 최적화한다:

| 단계 | 무엇을 하나 | 효과 |
|------|-----------|------|
| 1단계 | 숫자 정밀도를 절반으로 줄임 (float32 → float16) | 저장 공간 50% 절약 |
| 2단계 | 숫자 개수를 1536개 → 512개로 축소 | 추가 67% 절약 |
| 3단계 | 빠른 검색용 256개 숫자 버전을 추가 생성 | 검색 속도 3~5배 향상 |

비유: 도서관의 책 분류 시스템처럼, 먼저 256개 숫자로 "대략 이 근처" 후보를 빠르게 추린 뒤, 512개 숫자로 "정확히 이것" 최종 결과를 찾는다.

**개인정보 보호**: 임베딩 전에 주민번호, 전화번호, 환자 이름 등 민감 정보가 포함되어 있으면 자동으로 차단한다. 단, "원장님", "선생님" 같은 일반적 호칭은 허용한다.

### 2.4 검색 — 질문에 맞는 자료를 찾는 과정

환자 질문이 들어오면, 벡터DB에서 관련 자료를 찾는다.

**검색 우선순위 (뭘 먼저 찾나)**:

```
1순위: 의사 고유 스타일 (이 의사는 보통 어떻게 설명하나?)
2순위: 병원 정책 (진료시간, 가격, 검사 준비사항 등)
3순위: 환자 기록 (이 환자의 EMR, 검사결과 등)
4순위: 학습된 대화 (과거에 비슷한 질문에 어떻게 답했나?)
```

**데이터 격리 (Wall RAG)**: A 병원 의사의 자료가 B 병원에서 절대 검색되지 않는다. 의사별로 완전히 분리된 "벽"이 있다.

**검색 결과 정제 — 3단계 깔때기**:

```
[1차] 의미 유사도로 50개 후보 추출
       → "이 질문과 비슷한 의미의 자료 50개를 가져와"
       ↓
[2차] 하이브리드 재정렬로 12개 선택
       → 의미 유사도(50%) + 키워드 매칭(30%) + 소스 중요도(20%) 종합 점수
       → "혈압약"이라는 단어가 정확히 들어있는 자료에 가산점
       ↓
[3차] AI 재평가로 6~8개 최종 선택 (선택적)
       → 소형 AI(GPT-4o-mini)가 "이 자료가 진짜 질문에 관련 있는지" 한번 더 판단
       ↓
[최종] 토큰 예산에 맞춰 자료 선택
```

**질문 확장**: "혈압약 언제 먹어요?"라는 질문을 AI가 자동으로 확장한다:
- "고혈압 약물 복용 시간"
- "항고혈압제 투약 스케줄"
→ 이렇게 변형된 질문으로도 검색하여 더 많은 관련 자료를 찾는다.

### 2.5 환자 요약지 (Patient Wiki) — Karpathy LLM Wiki 패턴

**문제**: 환자가 183회 방문했다면, 매번 질문할 때마다 183건의 기록을 전부 검색해야 할까?

**해결**: 환자별로 미리 "요약지"를 만들어둔다.

**비유**:
> 의사가 환자를 볼 때, 매번 분기별 기록을 하나하나 뒤지지 않는다.
> 간호사가 미리 정리해둔 **"환자 요약지"** 를 보고 빠르게 파악한다.
> 닥톡 AI도 똑같이 한다.

**요약지 구성**:

```
환자 BIT-97932 요약지
────────────────────
핵심 정보: 고혈압, 당뇨(2형), 고지혈증
현재 처방: 아모디핀 5mg, 메트포르민 500mg ...
최근 검사: 혈당 126, HbA1c 6.8 (2024-03-15)
주요 증상: 어지러움, 두통 호소
방문 이력: 최근 5회 방문 요약
────────────────────
```

**작동 방식**:
1. 환자에 대한 질문이 오면, 먼저 요약지가 있는지 확인
2. 요약지가 있으면 → 요약지를 AI에게 전달 (빠르고 정확)
3. 요약지가 없으면 → 원본 데이터를 검색 (일반 RAG 방식)

**자동 업데이트**: 새 데이터가 추가되면 기존 요약지를 폐기하고, 다음 질문 시 최신 데이터로 자동 재생성한다.

**비용**: LLM을 호출하지 않고 데이터를 구조적으로 정리하는 방식이라 추가 비용이 0원이다.

---

### 2.6 컨텍스트 구성 — AI에게 전달할 "쪽지" 만들기

AI에게 무한한 양의 자료를 줄 수 없다. **토큰 예산** 안에서 가장 중요한 정보만 골라 전달해야 한다.

**토큰 예산 분배**:

| 구성 요소 | 예산 | 비유 |
|----------|------|------|
| 환자 정보 (요약지 또는 Facts+Sources) | 1100 토큰 | A4 반 페이지 분량 |
| 과거 대화 기록 | 400 토큰 | A4 1/4페이지 분량 |
| RAG 검색 결과 (의사 지식, 병원 정책 등) | 3000 토큰 | A4 한 페이지 분량 |

**Lost-in-the-Middle 방지**:

AI는 전달받은 자료의 맨 앞과 맨 뒤에 더 집중하는 특성이 있다. 가운데 내용은 상대적으로 덜 주의를 기울인다. 이 문제를 해결하기 위해:
- 가장 중요한 자료 → 맨 앞에 배치
- 두 번째로 중요한 자료 → 맨 뒤에 배치
- 나머지 → 가운데에 배치

**출처 표시**: AI 답변에 "[1]", "[2]" 같은 인용 번호를 달아 어떤 자료를 참고했는지 표시한다.

---

### 2.7 안전 장치 — 의료 AI의 생명선

의료 AI는 잘못된 답변이 환자 생명에 영향을 줄 수 있다. 닥톡은 **이중 안전 장치**를 적용한다.

**입력 안전 검사 (Pre-check) — 환자가 말하기 전에**:

| 감지 대상 | 예시 | 대응 |
|----------|------|------|
| 응급 상황 | "가슴이 너무 아파요", "숨을 못 쉬겠어요" | 즉시 119/응급실 안내 (AI 답변 대신) |
| 정신건강 위기 | "죽고 싶어요", "자해하고 싶어요" | 즉시 자살예방상담전화 1393 안내 |
| 소아 응급 | "아기가 열이 40도예요" | 즉시 소아응급실 방문 안내 |

응급 상황 감지 시에는 AI가 답변을 생성하지 않고, 미리 준비된 응급 안내 메시지를 즉시 보여준다.

**출력 안전 검사 (Post-check) — AI가 답한 후에**:

| 검사 항목 | 문제 | 자동 조치 |
|----------|------|----------|
| 확정 진단 | "확실히 당뇨입니다" | → "당뇨일 가능성이 있습니다" |
| 약물 용량 | "하루 3번 500mg 드세요" | → "정확한 복용량은 담당 의사에게 확인하세요" |
| 개인정보 노출 | 주민번호, 전화번호 포함 | → "[개인정보 마스킹]"으로 대체 |
| 면책 문구 누락 | 답변에 의사/진료 언급이 없음 | → "정확한 진단은 담당 의사에게 확인하세요" 자동 추가 |

**개인정보 보호 (PHI Guard)**:
- AI에게 보내는 요청에도 개인정보가 포함되어 있는지 검사
- 환자 이름을 절대 부르지 않음 → "환자분" 또는 차트번호로 호칭
- 한국 내 데이터 잔류(Data Residency) 보장

---

### 2.8 AI 모델 — 누가 답변을 생성하나

닥톡은 용도별로 다른 AI 모델을 사용한다.

| 용도 | 모델 | 왜 이 모델? |
|------|------|-----------|
| 환자 채팅 (기본) | Google Gemini 2.5 Flash | 빠르고 저렴, 한국어 우수 |
| 환자 채팅 (예비) | OpenAI GPT-4o | Gemini 장애 시 자동 전환 |
| 검색 결과 재정렬 | GPT-4o-mini | 작고 빠른 모델로 비용 효율적 |
| 질문 확장 | GPT-4o-mini | 동일 |
| 상담 요약 | Gemini Flash | 빠르고 저렴 |
| 텍스트 임베딩 | OpenAI text-embedding-3-small | 한국어 임베딩 성능 우수 |

**자동 복구**: Gemini에 문제가 생기면 자동으로 GPT-4o로 전환된다. 서비스가 완전히 멈추는 일을 방지한다.

**의사 페르소나**: AI는 단순히 답변을 생성하는 것이 아니라, 해당 의사의 말투와 진료 스타일을 학습하여 "의사의 분신"처럼 대화한다. 한의원이면 한의학 용어(기허, 어혈, 침술 등)도 쉽게 풀어서 설명한다.

---

### 2.9 상담 자동 요약

상담이 끝나면 AI가 전체 대화를 자동 요약하여 의사에게 제공한다.

**요약 내용**:
- 전체 상담 요약 (3~5문장)
- 환자의 주요 증상 목록
- AI가 제안한 권장 사항 목록
- 대화 건수 및 상담 시간

**활용**: 의사가 전체 대화를 읽지 않아도 핵심만 빠르게 파악할 수 있다. 전자차트에 바로 기록할 수 있는 형태로 제공된다.

---

### 2.10 병원 정보 자동 채우기

병원이 처음 가입할 때, 요양기관 코드만 입력하면 건강보험심사평가원(HIRA) 공공 API에서 병원 정보를 자동으로 가져온다.

| 자동 채우기 항목 | 데이터 출처 |
|----------------|-----------|
| 병원명, 주소, 전화번호 | HIRA API |
| 진료과, 병원 종류 (의원/병원/종합병원) | HIRA API |
| 위도/경도 (지도 표시용) | HIRA 또는 카카오 지도 API |
| 개설일 | HIRA API |

안전 정책: 의사가 수동으로 입력한 값은 절대 덮어쓰지 않는다. 비어있는 항목만 자동으로 채운다.

---

### 2.11 의학 논문 검색 (PubMed 연동)

AI가 답변할 때 근거가 부족하면, PubMed(미국 국립의학도서관)에서 관련 논문을 자동 검색한다.

- 한국어 의학 용어를 영어로 자동 변환 (당뇨 → diabetes mellitus)
- 논문 제목, 저자, 학술지, 출판일 정보를 가져옴
- 답변에 논문 인용을 첨부할 수 있음

---

### 2.12 Compound 학습 — AI가 점점 똑똑해지는 구조

닥톡 AI는 사용할수록 똑똑해진다.

```
환자가 질문 → AI가 답변 → 답변 내용을 환자 기록에 저장
                                    ↓
                        다음에 같은 환자가 질문하면
                        이전 AI 답변도 참고하여 더 나은 답변 생성
```

이것이 Karpathy가 말하는 **Compound 패턴**: AI의 출력이 다시 입력이 되어 지식이 축적되는 구조.

## Part 3. Karpathy LLM Wiki 패턴 — 어디서 왔고, 무엇을 더 배울 수 있나

---

### 3.1 Andrej Karpathy는 누구인가

Tesla의 AI 책임자를 역임하고 OpenAI 창립 멤버인 AI 분야의 세계적 권위자. 그가 제안한 "LLM Wiki" 패턴은 RAG의 한계를 넘어서는 새로운 접근법이다.

### 3.2 핵심 아이디어 — "매번 찾지 말고, 미리 정리해두자"

**기존 RAG의 한계**:
> 매번 질문이 올 때마다 원본 문서에서 지식을 다시 찾아야 한다.
> 마치 도서관에서 매번 같은 책을 꺼내 같은 페이지를 펼치는 것.

**Karpathy의 제안**:
> LLM이 자료를 읽고, 미리 정리된 "위키"를 만들어두자.
> 질문이 오면 원본이 아니라 위키를 참조하면 된다.
> 새 자료가 들어오면 위키를 업데이트하면 된다.

### 3.3 3-Layer 아키텍처

| Layer | 역할 | 비유 | 닥톡 적용 |
|-------|------|------|----------|
| Raw Sources (원본) | 원본 자료. 절대 수정 안 함 | 도서관의 원본 도서 | 환자 기록, 업로드 파일 |
| Wiki (요약) | LLM이 정리한 요약 문서 | 교수가 정리한 강의 노트 | 환자 요약지 (Patient Wiki) |
| Schema (규칙) | 위키를 어떻게 구성할지 규칙 | 강의 노트 작성 가이드라인 | 코드에 내장 |

### 3.4 3가지 핵심 작업

| 작업 | 설명 | 비유 |
|------|------|------|
| **Ingest (수집)** | 새 자료를 읽고 위키를 업데이트 | 새 논문이 나오면 강의 노트에 반영 |
| **Query (질의)** | 위키에서 답을 찾고, 가치 있으면 위키에도 반영 | 학생 질문에 답하다가 좋은 예시가 나오면 노트에 추가 |
| **Lint (검수)** | 위키의 품질을 주기적으로 점검 | 강의 노트에 오래된 정보나 모순이 없는지 체크 |

### 3.5 핵심 인사이트

> "지식 기반을 유지하는 데 있어 지루한 부분은 읽기나 사고가 아니라
> **북키핑(정리 작업)** 이다. LLM은 바로 이 정리 작업에 탁월하다."

사람이 할 일: 방향 설정, 큐레이션, 중요한 판단
AI가 할 일: 정리, 요약, 상호 참조, 업데이트 — 귀찮지만 필수적인 모든 작업

---

### 3.6 닥톡이 아직 적용하지 않은 것 & 발전 방향

| 미적용 항목 | 설명 | 기대 효과 |
|-----------|------|----------|
| **Lint (검수)** | 요약지에 모순이나 오래된 정보가 없는지 주기적 점검 | "당뇨 진단인데 혈당 처방이 없다" 같은 불일치 자동 감지 |
| **Index (목차)** | 병원 전체 환자의 요약지 카탈로그 | "당뇨 환자 목록", "최근 미방문 환자" 빠른 파악 |
| **Log (변경 기록)** | 요약지가 언제, 왜 변경되었는지 기록 | 감사 추적, "왜 이 정보가 바뀌었지?" 확인 가능 |
| **LLM 기반 지능형 요약** | 단순 나열이 아닌 임상적 해석이 포함된 요약 | "혈당이 3개월간 개선 추세" 같은 트렌드 분석 |
| **상호 참조** | 비슷한 환자 케이스, 관련 논문 자동 연결 | "비슷한 케이스 3건 참고" 기능 |
| **의사 피드백 학습** | 의사가 AI 답변을 수정하면 그것도 학습 | 요약지 품질이 점점 향상 |
| **위키 내 검색** | 요약지가 길어지면 위키 자체를 벡터 검색 | 대규모 환자일수록 효과적 |

## Part 4. 핵심 설계 원칙 요약

| 원칙 | 쉬운 설명 |
|------|----------|
| **미리 정리 > 그때그때 검색** | 환자 요약지를 미리 만들어두면, 매번 전체 기록을 뒤질 필요 없다 |
| **자동 갱신** | 새 데이터가 들어오면 요약지가 자동으로 최신화된다 |
| **지식 축적** | AI의 답변도 기록에 남아 다음번에 더 나은 답변으로 이어진다 |
| **요약지 우선** | 요약지가 있으면 원본 검색을 건너뛰어 속도와 정확도 모두 향상 |
| **다중 검색** | 의미 검색 + 키워드 검색 + AI 재평가로 삼중 확인 |
| **토큰 예산** | AI에게 줄 수 있는 분량 안에서 최적의 정보만 선별 |
| **이중 안전 장치** | 환자 입력 검사 + AI 출력 검사로 위험한 답변 차단 |
| **의사별 격리** | A 의사의 지식이 B 의사에게 절대 노출되지 않는다 |
| **벡터 최적화** | 저장 공간과 검색 속도를 극한까지 최적화 |
| **중요 정보 강조 배치** | AI가 잘 보는 위치(앞, 뒤)에 중요한 자료를 배치 |

| 역할 | 사용 기술 | 한 줄 설명 |

| 검색 결과 재정렬 | GPT-4o-mini | 가볍고 빠른 소형 AI 모델 |

| 개인정보 보호 | PHI Guard + Data Residency | 민감 정보 자동 차단 + 한국 내 데이터 보관 |
